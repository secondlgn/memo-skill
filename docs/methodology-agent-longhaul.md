# Agent 长程工程方法论 8 条（从 worldbox 项目 18 个 MVP 复盘提炼）

> 来源：一个"从零构建时空编排世界模型库"的 agent 项目复盘。
> 项目特征：单 agent 长程自主推进、用户少量高权重纠偏、无既有代码可依、目标是对齐一个旧系统的建模能力。
> 以下每条都是**实际走过的弯路**，不是推测的最佳实践。

## 1. 抽象是长出来的，不是设计出来的

**弯路**：MVP 计划阶段想"先设计完整类型系统再往里填"，被用户砍掉。后来所有真正的好抽象（运动主体、资源、派生路网）都是被需求探针逼出来的；预先设计的 Schema 一半字段没用上。

**方法论**：第一个 MVP 只做最小闭环（最小到近乎寒酸）。抽象的时机信号是"第二个需求出现了，且它和第一个需求在某个点上重复"。出现前不提取，出现后才提取。任何"将来可能需要"的字段都是负资产。

## 2. 归属问题是建模的第一问题

**弯路**：占用记录的主体归属（人？车？链？）到第 4 个 MVP 才想清楚，之前人被自己的车堵死。

**方法论**：建模任何"记录"前先回答三个归属：谁产生、谁拥有、谁能改。属性归属（能力跟着物体走 vs 跟着任务走）同理——用户一句"速度为什么不跟车走"暴露的就是这个。写第一个字段前先画归属表。

## 3. 凡是要比较的，第一天就结构化

**弯路**：用 `"drive:B>C"` 字符串标签做占用记录，对向冲突检测形同虚设，测试还全绿——直到 5 个 MVP 后才暴露。这是全程最隐蔽的坑。

**方法论**：一个字段如果将来要做匹配、比较、去重、方向判断，第一天就用结构化字段 + 规范化 key（如无向排序端点）。字符串拼接的"临时表示"会成为永久表示。测试通过不等于语义正确——单测只覆盖你想过的路径。

## 4. 几何/物理公式：先写语义，再写代码

**弯路**：转弯半径模型改了三次——方向反掉、内切圆用错，最后才落到切线法。每次改都牵连测试场景重调。

**方法论**：写公式前先用一句中文写"这个量在物理世界里是什么、变大意味着什么"，再写自洽性检查（直行/极端情况下公式退化成什么）。公式错了测试抓不住——测试只能抓"实现与意图不符"，抓不住"意图本身是错的"。

## 5. 每个近似都要当场标价

**弯路**："整段封锁路口""先来先服务"都是权宜近似，没标失效条件。结果死等 236 秒靠输出报告才暴露，消解策略重构了一圈。

**方法论**：写近似时同步写三样：近似了什么、什么时候失效、失效时怎么发现（哪个观测指标会异常）。"保守的错"也是错。有 TXT/日志这类人可读输出时，异常会自己浮出来——这是留证据通道的真正价值。

## 6. 检查函数与数据生产必须先对数据流

**弯路**：人力检查函数写完就测通过，但它假设的"员工占用记录"根本没人写入——单元绿、集成坏。

**方法论**：写检查/校验/断言类函数前，先画数据流图：谁生产数据、谁写入、在哪写入。检查函数测试时用的"手工构造数据"必须与真实生产路径同构，否则就是自欺。

## 7. 架构纪律要可执行，且第一天就建

**弯路**：分层（核/派生/求解/出口）、唯一写入口、依赖单向——这些纪律被 import 混乱逼出来时，重复定义和字符串标签已经存在。

**方法论**：纪律写成脚本（依赖方向扫描、写入口扫描），CI/每 tick 跑。纪律不可执行就不存在。允许的例外（如"检查层可写存量"）也要在脚本里显式声明，而不是口头默许。

## 8. 先读要对齐的真实系统，再做通用调研

**弯路**：RTS 引擎、开源仿真器、标准协议——通用调研做了三轮，而真正的锚点（要对齐的旧系统源码）很晚才打开。打开后发现 1/3 的"缺口"其实已有等价实现，另一些"必须做"的其实是旧系统的耦合病。

**方法论**：有对齐目标时，第一步就是通读目标系统的接口与数据结构，提炼"功能清单 + 等价映射"，之后的通用调研只补清单上的洞。调研的产出永远要落到"对本项目意味着什么"，否则是散光。

## 附：过程管理三条（同样来自实际教训）

- **用户纠偏是最高权重信号**：用户主动问"为什么 X"的地方，几乎必有一条原则被违反。当场把答案提炼成原则记下来（本项目"能力归物体"即如此产生）。
- **每阶段结束做回顾整理**：把逐条流水账降权归档，提炼的快照置顶。memo/笔记的前排必须只剩"仍然有效的注意力焦点"。
- **自动化驱动要匹配任务性质**：等外部事件用定时唤醒；纯本地连续工作直接连干到底，不要定时打断自己。
